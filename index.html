AI Agents 主題總覽（Synthesis & Overview）

本頁綜合 AI Agents LLM Wiki 已 Ingest 的 6 篇核心文獻（[[src-01]]、[[src-02]]、[[src-03]]、[[src-04]]、[[src-05]]、[[src-06]]），提供從初學者入門到工程實務落地的全景知識地圖。[src-01][src-02][src-04][src-05] ^p-ov-1

1. 什麼是 AI Agent？它跟一般 Chatbot 差在哪裡？

一般的大型語言模型（Chatbot）像是一位「只動口、不動手」的顧問：你問一句、它根據預訓練權重回一段文字，既不能主動查核外部事實，也無法替你執行多步驟任務；而 [[AI Agent（人工智慧代理）]] 則結合了 Brain（大腦 ＝ LLM 推論與規劃） 與 Body（身體 ＝ 外部工具與行動能力），能感知環境並獨立執行多步驟工作流以達成使用者目標。[src-04][src-05] ^p-ov-2

2. 底層積木與三大核心組件

所有代理系統的共同最小建構積木都是 [[Augmented LLM（擴充型語言模型）]]，並由三大核心組件支撐：(1) [[Planning（規劃）]] 負責透過 CoT / ToT 拆解子任務並進行自我反思；(2) [[Memory（記憶）]] 結合 Context Window 短期工作記憶與外部向量／Wiki 長期記憶；(3) [[Tool Use（工具使用）]] 透過 Data、Action、Orchestration 三類工具以及開放標準 [[Model Context Protocol (MCP)]] 與外部世界接軌。[src-01][src-02][src-04][src-06] ^p-ov-3

3. 核心運作迴圈：ReAct（邊想邊做）

為了避免純思考鏈（CoT）在封閉推論中產生幻覺，現代 Agent 普遍採用 [[ReAct（Reasoning + Acting）]] 迴圈，交替執行 Thought（思考下一步）→ Action（呼叫外部工具）→ Observation（觀察環境回傳結果），將外部真實證據不斷帶回上下文視窗。[src-03][src-02] ^p-ov-4

4. 架構選型、多代理與安全護欄

在工程實務上，系統設計沿著連續的 [[自主性光譜（Agency Spectrum）]] 展開：若步驟可事先預期，應優先使用確定性的 [[5 種常見 Workflow 模式]]（Prompt Chaining、Routing、Parallelization、Orchestrator-Workers、Evaluator-Optimizer）；只有面對複雜決策、難維護的規則或非結構化資料時（見 [[when-to-use-agents]]），才升級為自主 Agent 或 [[Multi-Agent 多代理系統（Manager 與 Decentralized Handoff）]]，並搭配多層次 [[Guardrails 安全護欄與 Human-in-the-loop]] 確保安全可控。[src-01][src-04][src-05] ^p-ov-5

討論 #1 — src-01: Anthropic《Building Effective Agents》

  • 核心 Takeaways：
  • Anthropic 將廣義的「Agentic Systems（代理型系統）」一分為二：Workflows（工作流） 是由預先寫好的程式碼路徑來編排 LLM 與工具；Agents（自主代理） 則是由 LLM 自己動態決定工作流程與工具使用方式。
  • 所有代理系統的地基都是 Augmented LLM（擴充型 LLM）：在基礎模型上加上檢索（Retrieval）、工具（Tools）與記憶（Memory）。
  • 實務上最常見的 5 種 Workflow 組裝模式：Prompt Chaining（提示串接）、Routing（路由分流）、Parallelization（平行化：Sectioning 與 Voting）、Orchestrator-Workers（協調者－工兵）、Evaluator-Optimizer（評估－優化迴圈）。
  • 核心工程原則：永遠從最簡單的方案（單一 LLM 呼叫或 Workflow）開始，只有在任務無法預先寫死步驟時才使用自主 Agent，因為 Agent 會帶來更高的延遲與成本。

討論 #2 — src-02: Lilian Weng《LLM Powered Autonomous Agents》

  • 核心 Takeaways：
  • 提出最經典的 Agent 三大組件公式：$\text{Agent} = \text{LLM Brain} + \text{Planning} + \text{Memory} + \text{Tool Use}$。
  • Planning（規劃） 包含兩面向：(a) Task Decomposition（任務拆解），如 Chain of Thought (CoT)、Tree of Thoughts (ToT)；(b) Self-Reflection（自我反思），如 ReAct、Reflexion，讓模型從過去的失敗行動中修正策略。
  • Memory（記憶） 類比人類記憶系統：感官記憶（嵌入表示）、短期記憶（Short-term Memory = 模型的 Context Window 上下文視窗）、長期記憶（Long-term Memory = 外部向量資料庫／知識庫，透過快速檢索讀寫）。
  • Tool Use（工具使用） 讓突破模型權重凍結的限制（如 MRKL、Toolformer、HuggingGPT、API-Bank）。

討論 #3 — src-03: Yao et al.《ReAct: Synergizing Reasoning and Acting in Language Models》

  • 核心 Takeaways：
  • 傳統 Chain-of-Thought (CoT) 只在模型內部做封閉式推論，無法接觸外部世界，容易產生事實幻覺（Hallucination）並一路錯到底；純 Acting 則缺乏高階規劃與工作記憶。
  • ReAct 讓模型交錯產生 Thought（推論軌跡）→ Action（呼叫外部環境／工具）→ Observation（取得環境回饋）。
  • 實證結果：在知識密集任務（HotPotQA、FEVER）上透過查閱 Wikipedia API 克服了 CoT 的幻覺問題；在決策互動任務（ALFWorld、WebShop）上大幅超越純模仿學習與強化學習基準，且推論軌跡具人類可讀性與可除錯性。

討論 #4 — src-04: OpenAI《A Practical Guide to Building Agents》

  • 核心 Takeaways：
  • 定義 Agent 的三個實作基礎組件：Model（模型大腦）、Tools（Data / Action / Orchestration 三類工具）、Instructions（明確的指令、邊界與例外處理規範）。
  • 提出何時該建立 Agent 的三大判準：(a) 複雜且需依情境權衡的決策（如退款審核）；(b) 傳統規則引擎（if-else）過於龐大難維護（如資安審查）；(c) 高度仰賴非結構化資料（如自然語言對話、文件與圖片理賠）。
  • 單一代理優先，必要時才拆分為多代理（Multi-Agent），並將多代理分為兩種拓樸：Manager pattern（經理模式：中央代理把子代理當工具呼叫） 與 Decentralized pattern（去中心化模式：平輩代理透過 Handoff 移交控制權）。
  • Guardrails（安全護欄）必須採多層防禦（Defense-in-depth）：結合理性分類器、PII 個資過濾、工具風險分級（低／中／高風險），以及高風險操作前的 Human-in-the-loop（人類介入確認）。

討論 #5 — src-05: Hugging Face Agents Course《Unit 1: What are Agents?》

  • 核心 Takeaways：
  • 專為初學者設計的定義：AI Agent 是一個利用 AI 模型與環境互動，以達成使用者設定目標的系統，具備兩大部位：Brain（AI 模型負責思考與規劃） 與 Body（工具與能力負責執行動作）。
  • 自主性光譜（Spectrum of Agency）：代理性不是非黑即白（0 或 1），而是連續光譜——從完全沒有自主性的簡單輸出、路由分流、多步驟工作流，一路到能自行決定迭代次數與控制流的自主 Agent。
  • 直觀生活比喻：一般 LLM 就像只會動口回答問題的顧問；AI Agent 則像有手有腳、能幫你查行事曆、訂機票、寄信的數位助理。

AI Agent（人工智慧代理）

AI Agent（人工智慧代理） 是一個利用 AI 模型與其外部環境互動，以獨立完成使用者所設定目標的系統；與只會被動「一問一答」的傳統聊天機器人（Chatbot）不同，Agent 能主動拆解步驟、呼叫外部工具並根據環境回饋修正行為。[src-04][src-05] ^p-agent-1 從初學者的直觀比喻來看（參見 [[Hugging Face Agents Course]]），一個 AI Agent 就像擁有兩個核心部位的數位助理：Brain（大腦 ＝ 語言模型 LLM） 負責思考、推論與規劃下一步；Body（身體 ＝ 工具與能力 Tools & Capabilities） 則賦予它在真實世界行動的手腳，例如搜尋網頁、查詢資料庫、寄送電子郵件或執行程式碼。[src-05] ^p-agent-2 從系統架構的角度來看，[[Lilian Weng (2023)]] 提出最具代表性的自主代理三大支柱公式：以 LLM 作為核心控制器，外加 [[Planning（規劃：子任務拆解與自我反思）]]、[[Memory（記憶：短期上下文視窗與長期向量知識庫）]] 以及 [[Tool Use（工具使用：呼叫外部 API 與工具）]]。[src-02] ^p-agent-3 而在工程實作層面，[[OpenAI (2025)]] 將每一個可運行的 Agent 濃縮為三個基礎要素（Foundational Components）：(1) Model（驅動推論與決策的 LLM）；(2) Tools（代理可用來讀取資料或執行動作的外部函數與 API）；(3) Instructions（開發者設定的明確行為準則、工作步驟與安全邊界）。[src-04] ^p-agent-4 要特別注意的是，[[Anthropic (2024)]] 與 [[Hugging Face (2025)]] 都強調「代理性（Agency）」是一條連續的 [[自主性光譜（Spectrum of Agency）]]：從步驟由程式碼固定編排的確定性 Workflow（工作流），一路延伸到由模型動態決定控制流與迴圈次數的高自主 Autonomous Agent。[src-01][src-05] ^p-agent-5

Augmented LLM（擴充型語言模型）

根據 [[Anthropic《Building Effective Agents》]]，不論是確定性的 [[Workflow]] 還是高自主性的 [[Agent]]，它們最底層的基本建構積木（building block）都是 Augmented LLM（擴充型語言模型）。[src-01] ^p-aug-1 單純的預訓練語言模型只能根據訓練截止前的參數權重產生文字；而 Augmented LLM 則在模型外圍加上三種關鍵擴充能力：Retrieval（檢索外部知識）、[[Tools（呼叫外部工具）]] 與 [[Memory（讀寫短期與長期記憶）]]，且現代模型已能主動決定何時產生搜尋查詢、選用哪個工具、以及哪些資訊應該保留到記憶中。[src-01][src-02] ^p-aug-2 在實作 Augmented LLM 的外部連接時，工程團隊可以使用自訂函數呼叫（Function Calling），或是採用 [[Anthropic 開源的 Model Context Protocol (MCP)]] 標準協議，以統一的 Client-Server 介面掛載本地與遠端的資料源和工具。[src-01][src-06] ^p-aug-3

Guardrails & Human-in-the-Loop（多層次安全護欄与人機協作）

因為自主 [[AI Agent]] 能夠呼叫 [[外部動作工具]] 實際修改資料庫、發送郵件或執行交易，一旦發生推論錯誤或遭受惡意提示注入（Prompt Injection），後果遠比一般聊天機器人嚴重；[[Anthropic (2024)]] 與 [[OpenAI (2025)]] 都強調，生產環境的 Agent 必須配置嚴格的 Guardrails（安全護欄） 與檢查點。[src-01][src-04] ^p-grd-1 [[OpenAI《A Practical Guide to Building Agents》]] 指出，Guardrails 不應只依賴單一規則，而應建構 多層防禦體系（Layered Defense-in-Depth），涵蓋：(1) Relevance classifier（相關性分類器） 攔截超出代理職責範圍的離題請求；(2) Safety classifier（安全分類器） 偵測越獄（Jailbreaks）與提示詞注入攻擊；(3) PII filter（個資過濾器） 防止身分證號、信用卡等敏感個人資料外洩；(4) Moderation 與 Output validation（內容審核與輸出格式／品牌規範驗證）。[src-04] ^p-grd-2 針對 [[工具呼叫安全（Tool Safeguards）]]，[[OpenAI]] 建議為每一個工具進行 風險分級（Low / Medium / High Risk）：根據工具是「唯讀（read-only）或寫入（write）」、「是否可逆（reversibility）」、「所需權限範圍」與「是否涉及金錢財務影響」來決定管控強度；唯讀低風險工具可自動放行，而像「大額退費、刪除生產資料、發送全體通知」等高風險或不可逆動作則必須攔截。[src-04][src-01] ^p-grd-3 最後一道關鍵防線是 Human-in-the-loop（人類介入機制） 與 沙盒環境（Sandboxed testing）：當 Agent 超過最大重試／失敗次數門檻（failure threshold）仍無法完成任務，或是即將執行高風險敏感動作時，系統必須自動暫停並移交給人類審核批准（或在隔離的 Sandbox 中先完成驗證），同時兼顧系統自主性與操作安全性（也彌補 [[Lilian Weng]] 指出的長程規劃錯誤恢復難題）。[src-01][src-02][src-04] ^p-grd-4

MCP（Model Context Protocol，模型上下文協議）

Model Context Protocol (MCP) 是由 [[Anthropic 開源的開放標準協議]]，專門用來統一應用程式如何向大型語言模型提供外部上下文資料（Context）與 [[工具呼叫能力]]。[src-06] ^p-mcp-1 官方以 「AI 應用程式的 USB-C 連接埠」 來比喻 MCP：在沒有 MCP 之前，如果世界上有 $N$ 個 AI 應用（IDE、聊天介面、Agent 框架）想要連接 $M$ 個外部系統（Google Drive、Slack、GitHub、PostgreSQL），社群必須重複撰寫 $N \times M$ 套客製化連接器；透過 MCP 標準協議，每個工具只需實作一次 MCP Server，所有支援 MCP 的 AI 應用就能直接插上使用，將整合複雜度降為 $N + M$。[src-06] ^p-mcp-2 MCP 的運作建立在清晰的 Host / Client / Server 三層架構 之上：(1) MCP Hosts 是需要透過 MCP 取得資料或呼叫工具的 AI 應用程式（如 Claude Desktop、AI 程式碼編輯器或 [[Agent]] 系統）；(2) MCP Clients 內嵌於 Host 之中，負責與特定的 Server 維持一對一（1:1）的雙向協議連線；(3) MCP Servers 則是輕量級服務程式，負責將本地資料源（Local Data Sources，如本機檔案、SQLite 資料庫）或遠端服務（Remote Services，如外部 REST API）封裝成標準的 Resources、Tools 與 Prompts 供模型安全調用。[src-06][src-01] ^p-mcp-3

Memory（記憶系統）

[[Lilian Weng (2023)]] 將 [[AI Agent]] 的記憶機制對照人類心理學的記憶分類，分為感官記憶（Sensory Memory，對應文字或影像的 Embedding 嵌入向量表示）、短期記憶（Short-term Memory） 與 長期記憶（Long-term Memory）。[src-02] ^p-mem-1 短期記憶（Short-term / Working Memory） 直接對應大型語言模型的 上下文學習（In-context Learning）：所有當前對話紀錄、工具回傳的觀察結果與進行中的子任務狀態都放在 Context Window 內，直接受限於模型的上下文視窗長度上限（finite context window length）。[src-02] ^p-mem-2 長期記憶（Long-term Memory） 則是讓 Agent 在啟動時或執行過程中可以隨時查詢與寫入的 外部持久儲存空間（External Persistent Storage），常見實作包含以近似最近鄰搜尋（ANN / MIPS，如 FAISS、HNSW）加速的外部向量資料庫，或是像本專案一樣由 LLM 結構化維護並建立雙向連結與 index.md 目錄的持久知識庫（LLM Wiki）。[src-01][src-02] ^p-mem-3 結合短期與長期記憶，能讓 [[Augmented LLM]] 在跨回合甚至跨工作階段（cross-session）中保留使用者偏好、歷史經驗與領域知識，避免每次詢問都從零開始重新推導。[src-01][src-02] ^p-mem-4

Multi-Agent Systems（多代理系統）

在設計 [[AI Agent]] 時，[[OpenAI《A Practical Guide to Building Agents》]] 提出的黃金法則是：永遠先從單一代理（Single-agent system）開始，透過逐步增加 [[工具]] 與結構化指令來擴充能力，而不是一開始就建立複雜的多代理網路。[src-04] ^p-ma-1 什麼時候才需要把單一代理拆分成 Multi-Agent System（多代理系統）？[[OpenAI (2025)]] 指出兩個明確訊號：(1) 複雜指令與多重分支（Complex logic）：當單一提示詞塞滿太多條件分支與例外規則，導致模型難以穩定遵守時；(2) 工具過載（Tool overload）：當單一代理掛載了太多名稱、參數或功能重疊的工具，即使改善工具說明仍常選錯工具時。[src-04] ^p-ma-2 多代理系統在架構上主要分為兩種協作拓樸：第一種是 Manager Pattern（經理／中央調度模式，又稱 Agents as Tools），由一個中央 Manager Agent 掌握與使用者的對話控制權，並透過編排型工具（Orchestration tools）在幕後呼叫多個專職子代理（如翻譯代理、研究代理、帳務代理）後彙整回答，這與 [[Anthropic 的 Orchestrator-Workers 模式]] 相呼應。[src-04][src-01] ^p-ma-3 第二種是 Decentralized Pattern（去中心化／平輩交棒模式），多個專職代理處於平等地位，當負責初步分流的 Triage Agent 判斷問題屬於「訂單退換貨」或「技術維修」時，會執行 Handoff（單向控制權移交），把整段對話狀態與後續主導權直接交棒給該領域的專職代理接手與使用者互動。[src-04][src-05] ^p-ma-4

Planning（規劃：任務拆解與自我反思）

在 [[Lilian Weng (2023)]] 的自主代理架構中，面對複雜的多步驟任務，[[AI Agent]] 不能直接一步跳到答案，必須依賴 Planning（規劃） 組件，其核心包含兩大機制：Task Decomposition（任務拆解） 與 Self-Reflection（自我反思與修正）。[src-02] ^p-plan-1 Task Decomposition（任務拆解） 的目標是將大問題拆解成較小、可管理的子目標（subgoals）：常見方法包括 Chain of Thought (CoT，思考鏈) 要求模型「一步一步思考（think step by step）」；以及 Tree of Thoughts (ToT，思考樹) 在每一步產生多個候選思考分支，透過廣度優先（BFS）或深度優先（DFS）搜尋並評估最佳路徑。[src-02] ^p-plan-2 任務拆解也可以透過三種不同模式完成：(1) 直接由 LLM 以提示詞拆解；(2) 依賴任務專屬指令（例如寫作大綱步驟）；或 (3) 交給外部古典規劃器（如 LLM+P 將問題轉為 PDDL 規劃描述語言）。[src-02] ^p-plan-3 Self-Reflection（自我反思） 則讓 Agent 具備從過去失敗或環境回饋中學習與修正的能力：最核心的代表是 [[ReAct（Thought → Action → Observation）]] 在每步動作後根據環境觀察調整計畫，以及 Reflexion 框架透過動態記憶與自我檢討文字回饋，在不更新模型權重的情況下改善下一輪決策。[src-02][src-03] ^p-plan-4

ReAct（Reasoning + Acting）：邊想邊做的核心迴圈

由 [[Yao et al. (2022)]] 提出的 ReAct（Reasoning + Acting） 是現代 [[AI Agent]] 最核心的執行迴圈典範，它讓語言模型以交錯（interleaved）的方式循環執行三個步驟：Thought（思考／推論）→ Action（呼叫工具或執行動作）→ Observation（從外部環境接收觀察結果）。[src-03][src-05] ^p-react-1 為什麼不能只用純 Chain-of-Thought (CoT，思考鏈)？[[ReAct 論文]] 指出，純 CoT 屬於「封閉式內部推論」，模型只靠自身參數憑空想像步驟，沒有與外部真實世界接觸，因此一旦中途記錯事實就會產生 幻覺（Hallucination） 並將錯誤一路向下傳播（error propagation）；相反地，純 Acting 缺乏高階推論規劃，容易在複雜環境中迷失方向。[src-03] ^p-react-2 在 ReAct 的每一個循環中：Thought（思考） 負責拆解目標、追蹤進度、分析上一步的結果並決定下一步計畫（見 [[planning]]）；Action（行動） 負責呼叫外部 [[工具或 API]]（例如 Search[問題] 或 Lookup[關鍵字]）；Observation（觀察） 則把外部工具回傳的真實資料寫入短期 [[上下文記憶]]，讓下一輪的 Thought 有憑有據。[src-02][src-03] ^p-react-3 實驗證明，ReAct 在 HotPotQA 與 FEVER 等知識密集問答任務中透過查詢 Wikipedia API 顯著降低了幻覺；在 ALFWorld 家務互動與 WebShop 線上購物任務中，相比強化學習與模仿學習基準分別提升了 34% 與 10% 的絕對成功率，同時因為每一步都有明文 Thought 軌跡，人類工程師能輕易讀懂並除錯 Agent 的決策過程。[src-03] ^p-react-4

[src-03] ReAct: Synergizing Reasoning and Acting in Language Models

  • 作者：Shunyu Yao, Jeffrey Zhao, Dian Yu, Nan Du, Izhak Shafran, Karthik Narasimhan, Yuan Cao (Princeton University & Google Research)
  • 發表日期：2022-10-06 (ICLR 2023)
  • 原始檔案：raw/src-03-react-synergizing-reasoning-acting.md
  • 原文連結：https://arxiv.org/abs/2210.03629

核心主張與知識摘錄

過去的研究將語言模型的「推論（Reasoning，例如 Chain-of-Thought 思考鏈）」與「行動（Acting，例如產生動作指令）」視為兩個獨立主題。純 CoT 僅仰賴模型內部參數進行封閉推論，無法與外部世界互動，因此在多步推論中容易產生事實幻覺（hallucination）與錯誤傳播（error propagation）。[src-03] ^p-src03-1 [[ReAct（Reasoning + Acting）]] 讓大型語言模型以交錯（interleaved）的方式同時產生 推論軌跡（Thought） 與 任務特定動作（Action），接著從外部環境或工具接收 觀察結果（Observation），形成 Thought → Action → Observation 的閉環迴圈。[src-03] ^p-src03-2 在這個迴圈中，推論軌跡（Thought） 幫助模型誘導、追蹤並更新行動計畫（induce, track, and update action plans）以及處理例外狀況；而 動作（Action） 則讓模型能主動查詢外部知識源（如 Wikipedia API）或操作環境，將外部真實資訊帶回上下文視窗中。[src-03] ^p-src03-3 在實驗驗證中，ReAct 在知識密集推論基準（HotPotQA 多跳問答、FEVER 事實查核）上透過與簡單 Wikipedia API 互動，有效克服了純 CoT 的幻覺問題；在互動決策基準（ALFWorld 文字遊戲與 WebShop 線上購物環境）上，僅用 1 到 2 個上下文範例就顯著超越模仿學習與強化學習方法，在 ALFWorld 與 WebShop 分別取得 34% 與 10% 的絕對成功率提升，且具備極高的人類可解釋性與可除錯性。[src-03] ^p-src03-4

[src-04] A Practical Guide to Building Agents (OpenAI)

  • 作者：OpenAI
  • 發表日期：2025-04
  • 原始檔案：raw/src-04-openai-practical-guide-building-agents.md

核心主張與知識摘錄

OpenAI 將 [[Agent（代理）]] 定義為能代表使用者獨立完成多步驟工作流的系統，其底層由三個基礎要素組成：(1) Model（負責推論與決策的語言模型）；(2) Tools（讓代理與外部系統互動的外部函數或 API）；(3) Instructions（明確規範代理行為、步驟與邊界的指引與安全規範）。[src-04] ^p-src04-1 關於 [[何時該打造 Agent]]，OpenAI 提出三個高價值應用場景判準：(1) Complex decision-making（需要細膩判斷、例外處理與情境敏感度的複雜決策，例如客服退費審核）；(2) Difficult-to-maintain rules（傳統 if-else 規則引擎變得過於龐大脆弱、難以維護的系統，例如廠商資安審查）；(3) Heavy reliance on unstructured data（需要理解自然語言文件、對話或非結構化資料的工作，例如保險理賠審理）。[src-04] ^p-src04-2 在 [[工具設計]] 上，OpenAI 將代理所需的工具歸為三大類：Data tools（查詢資料庫、讀取 PDF、網頁搜尋或 RAG 檢索以取得背景資訊）、Action tools（寄送 Email、更新 CRM 紀錄、呼叫外部服務執行變更動作）、以及 Orchestration tools（把其他專門的 Agent 當作工具來呼叫）。[src-04] ^p-src04-3 在系統拓樸上，OpenAI 建議先最大化單一代理（Single-agent system）的能力，當指令過於複雜或工具過多導致容易選錯時，再拆分為 [[多代理系統（Multi-agent system）]]。多代理有兩種主要設計模式：Manager pattern（經理模式） 由一個中央 Manager 代理透過工具呼叫指揮多個專職子代理並保有對話控制權；Decentralized pattern（去中心化模式） 則是多個平輩代理透過 Handoff（單向移交） 將執行與對話控制權直接交棒給最適合的專職代理。[src-04] ^p-src04-4 在安全性上，OpenAI 強調 [[Guardrails（安全護欄）]] 必須採取多層防禦機制（layered defense），不可只靠單一防護：結合相關性分類器（Relevance classifier）、安全分類器（越獄與 Prompt Injection 偵測）、PII 個資過濾器、輸出驗證、工具風險分級（低／中／高風險，如退費或刪除資料），並在觸發高風險動作或超過失敗次數門檻時強制啟動 Human-in-the-loop（人類介入審核）。[src-04] ^p-src04-5

核心主張與知識摘錄

[src-06] Model Context Protocol (MCP) — Introduction

  • 作者：Anthropic / Model Context Protocol Open Source Project
  • 發表日期：2024-11-25

  • 原文連結：https://modelcontextprotocol.io/introduction

核心主張與知識摘錄

[[Model Context Protocol (MCP)]] 是一套開放標準協議（open protocol），用來標準化應用程式如何向大型語言模型（LLM）提供上下文（context）與工具連線。[src-06] ^p-src06-1 官方以 「AI 應用程式的 USB-C 連接埠」 來比喻 MCP：就像 USB-C 提供了一種標準化的實體介面讓電腦連接各種外接周邊與電源，MCP 也提供了標準化方式，讓 AI 模型與 Agent 連接不同的資料來源（Data Sources）與外部工具（Tools），解決過去每個模型與每個工具都必須各自撰寫客製整合的 $N \times M$ 碎片化問題。[src-06] ^p-src06-2 MCP 採用清晰的 Client-Server 三層架構：(1) MCP Hosts 是發起連線的 AI 應用程式（如 Claude Desktop、AI IDE 或各類 Agent 執行環境）；(2) MCP Clients 位於 Host 內部，負責與單一 Server 維持 1:1 的協議連線；(3) MCP Servers 是輕量級程式，透過標準化的 MCP 協議暴露特定能力（Tools、Resources、Prompts），並安全存取本地資料源（Local Data Sources，如本機檔案、資料庫）或遠端服務（Remote Services，如 Slack、GitHub 等 Web API）。[src-06] ^p-src06-3 對 [[Tool Use]] 與 [[Augmented LLM]] 而言，MCP 讓開發者能使用現成的預建整合（pre-built integrations），並在不同 LLM 供應商之間自由切換，同時將敏感憑證與資料存取權控制在自己的基礎設施與安全邊界之內。[src-06] ^p-src06-4

Tool Use（工具使用）

大型語言模型本身的參數權重在預訓練完成後即凍結，既不知道即時新聞或企業內部私有資料，也不擅長精確算術或直接操作外部軟體；Tool Use（工具使用） 正是為 [[AI Agent]] 裝上「感官與雙手（Body）」，讓模型能夠主動查詢外部世界並執行實際動作。[src-02][src-05] ^p-tool-1 根據 [[OpenAI《A Practical Guide to Building Agents》]]，實務上為 Agent 配置的工具可清楚分為三大類型：(1) Data tools（資料型工具），負責讀取與檢索上下文資訊，如查詢 SQL 資料庫、讀取 PDF、RAG 知識庫檢索或網頁搜尋；(2) Action tools（動作型工具），負責與外部系統互動並改變狀態，如發送 Email、建立行事曆事件、更新 CRM 紀錄或執行退費；(3) Orchestration tools（編排型工具），把另一個專職的 [[子代理（Sub-agent）]] 當作工具來呼叫。[src-04] ^p-tool-2 在學術與工業演進上，[[Lilian Weng (2023)]] 整理了從 MRKL 模組化路由、Toolformer 自監督學習 API 呼叫，到 HuggingGPT 以 LLM 當控制器調度多個專門模型的發展脈絡。[src-02] ^p-tool-3 [[Anthropic (2024)]] 特別提醒工程師：花在設計工具介面（Agent-Computer Interface, ACI）的心力應該與設計人類 UI 一樣多——要為每個工具撰寫極度清楚的參數說明、邊界條件與範例，進行防呆設計（poka-yoke），並可透過 [[Model Context Protocol (MCP)]] 標準化工具連接與透過 [[Guardrails]] 對高風險動作工具進行權限控管。[src-01][src-04][src-06] ^p-tool-4

When to Use Agents（何時該用與不該用 AI Agent）

面對新問題時，並非所有任務都適合做成自主 [[AI Agent]]。[[Anthropic (2024)]] 強調：應該尋找最簡單的解決方案，只有在確實需要時才增加系統複雜度——許多時候，單次 LLM 呼叫搭配檢索（RAG）或確定性的 [[Workflow]] 就已經足夠，因為自主 Agent 是以較高的延遲（latency）與 Token 成本（cost）來換取任務表現。[src-01] ^p-wtu-1 那麼什麼時候才真正值得導入 Agent？[[OpenAI (2025)]] 提出三個最具鑑別力的適用判準：(1) 複雜決策（Complex decision-making）——工作流程包含細微的情境判斷、多重例外處理，難以寫成死板規則（例如綜合考量購買紀錄與原因的客服退費審核）；(2) 難以維護的規則集（Difficult-to-maintain rules）——既有系統充斥數百條糾纏的 if-else 規則，每次新增條件都容易改壞舊邏輯（例如供應商資安合規審查）；(3) 高度依賴非結構化資料（Heavy reliance on unstructured data）——任務必須理解自然語言對話、PDF 合約或圖片內容才能推進（例如保險理賠審核）。[src-04] ^p-wtu-2 相對地，如果一個任務的每一個步驟都可以事先固定寫清楚、輸入資料高度結構化，或者應用場景對回應延遲極度敏感且完全零容錯，[[Anthropic]] 與 [[OpenAI]] 都建議直接採用確定性的程式碼或 [[Workflow]]，而不要強行套用開放式的自主 Agent；若確定採用 Agent，則必須搭配完善的 [[Guardrails 安全護欄]] 與沙盒測試環境。[src-01][src-04] ^p-wtu-3

5 種常見 Workflow 設計模式

在打造代理型系統時，[[Anthropic (2024)]] 總結出五種以 [[Augmented LLM]] 為積木、最常在生產環境使用的可組合 [[Workflow]] 設計模式（Composable Patterns）。[src-01] ^p-wf-1 模式一 Prompt Chaining（提示串接）：將一個任務拆成固定順序的多個步驟，前一步 LLM 的輸出成為下一步 LLM 的輸入，並且可以在任兩步中間插入程式化的檢查門檻（Programmatic Gate）以驗證格式或品質（例如先產生行銷文案大綱 → 檢查是否合規 → 撰寫正式文案 → 翻譯成多國語言）。[src-01] ^p-wf-2 模式二 Routing（路由分流）：先由一個分類器或輕量 LLM 判斷輸入屬於哪一種類型，再將其分發給專門為該類型最佳化的下游提示詞、工具或不同尺寸的模型（例如把一般常見客服問題導向快速的 Haiku/Flash 模型，把複雜技術問題或退費申請導向推理模型或專門流程）。[src-01] ^p-wf-3 模式三 Parallelization（平行化）：同時啟動多個 LLM 呼叫再以程式彙整結果，包含兩種變體——Sectioning（切分） 將任務切成獨立子任務平行處理（例如一個模型負責產生回答，另一個模型同時做 [[安全護欄審查]]），以及 Voting（投票） 對同一問題跑多次推論再取多數決以提升準確率（例如程式碼安全漏洞掃描）。[src-01] ^p-wf-4 模式四 Orchestrator-Workers（協調者－工兵模式）：當所需的子任務無法事先寫死時（例如跨多個檔案修改程式碼或進行多源深入研究），由一個中央 Orchestrator（協調者 LLM） 根據輸入動態拆解子任務並分派給多個 Workers（工兵 LLM），最後再由協調者彙整所有工兵的輸出。[src-01] ^p-wf-5 模式五 Evaluator-Optimizer（評估者－優化者迴圈）：由一個 Generator LLM 產生初稿，交給另一個 Evaluator LLM 依據明確標準進行評分與具體修改建議，若未達標則進入迴圈重新修正（這正是本作業建立 LLM Wiki 並透過 C2～C6 檢查節點反覆局部重新生成教學簡報所採用的核心模式）。[src-01] ^p-wf-6

Workflow vs Agent（工作流 vs 自主代理）

[[Anthropic《Building Effective Agents》]] 對「Agentic Systems（廣義代理系統）」做出了業界最重要的架構區分，將其分為 Workflows（工作流） 與 Agents（自主代理） 兩大類。[src-01] ^p-wva-1 Workflows（工作流） 是指「透過預先寫好的程式碼路徑（predefined code paths）來編排 LLM 與外部工具」的系統；步驟順序、分支條件與檢查點都由工程師在程式碼中固定，具備高度可預測性與穩定性，適合步驟清楚、結構固定的任務（參見 [[workflow-patterns]]）。[src-01] ^p-wva-2 Agents（自主代理） 則是指「由 LLM 自己動態決定流程（dynamically direct their own processes）與工具使用方式」的系統；模型會根據每一步環境回傳的觀察結果（如 [[ReAct 迴圈]]），自主決定要執行幾輪迴圈、下一步呼叫哪個 [[工具]]、以及何時判定任務完成或請求人類介入。[src-01][src-04] ^p-wva-3 [[Hugging Face Agents Course]] 進一步以 自主性光譜（Spectrum of Agency） 統合這兩者：代理性不是非黑即白，而是從 Level 0（單純模型輸出，無自主性）、Level 1（Routing 路由決定分支）、Level 2（確定性或半自主的多步 [[Workflow]] 與工具迴圈），一路延伸到 Level 3（模型完全掌控控制流、甚至觸發其他 [[子代理]] 的自主 Agent）。[src-01][src-05] ^p-wva-4
