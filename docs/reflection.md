## 二、兩次運行歷程關鍵事件記錄

### 1. v1 Baseline 遭遇的痛點
- 在沒有前置檢查的狀況下，大語言模型一路從大綱寫到最終 HTML。
- 最終驗證階段才發現：投影片第 8 頁引用的 MCP 概念與原始文獻定義出現語義偏差，且第 11 頁遺漏了段落錨點標籤。
- **後果**：由於沒有局部重新生成機制，必須整份 15 頁簡報全部打掉重寫，耗費大量等待時間與 API 配額。

### 2. v2 Shift-Left 的優化機制
- **左移檢驗（Shift-Left Testing）**：將質量檢驗盡可能推到流程的最前端。
- 在 `Node 2 Ingest` 後立即由 `Gate C2` 檢查錨點語法；在 `Node 6 Draft` 後立即由 `Gate C5` 事實查核器進行嚴格的比對。
- 當第 8 頁出現疑義時，Evaluator-Optimizer 僅鎖定第 8 頁數據並重新向 Wiki 檢索，單頁修正僅花費 4.2 秒即恢復正軌，順利通過後續所有節點。

## 三、核心反思與教學價值

1. **從 Prompt Engineering 到 Context Engineering**：
   單純追求提示詞的魔法咒語，無法保證長篇大論的穩定性。透過 Karpathy LLM Wiki 建立「客觀事實庫」，並用段落錨點約束生成，是徹底消除 AI 幻覺的最有效手段。
2. **Evaluator-Optimizer 是 Agent 穩定性的基石**：
   生成者（Generator）與審查者（Evaluator）職責分離，搭配明確的評判 Rubric 與回退迴圈，使系統展現出類似人類工程師的「自省與自我修正」能力。
3. **無依賴架構帶來的純粹與可移植性**：
   全專案 100% 純原生 HTML5 + CSS + JavaScript，零依賴外部打包工具，完美適配 GitHub Pages 靜態託管，展現出極致的工程簡潔美學。
